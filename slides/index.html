Part 1 · 問題

LLM 很聰明，但有四個毛病

幻覺

會自信地說出錯誤的內容

知識過時

只知道訓練時看過的資料

難以追溯

難以更新

共同的解法：把知識放在模型外面。今天介紹兩種做法。

Part 2 · RAG

RAG 是什麼？

回答之前，先去外部資料找相關內容，
再根據找到的內容回答。

Retrieval-Augmented Generation，檢索增強生成。名稱出自 Lewis 等人 2020 年的論文（NeurIPS 2020）。

參數記憶

訓練時「壓」進模型參數的知識（模型本身）

＋

非參數記憶

放在模型外面的資料（論文用 Wikipedia 的向量索引），用檢索器去查

Part 2 · RAG

RAG 怎麼運作？四個步驟

① 事先做

索引

把資料切成 chunk、轉成 embedding，存進可依意思搜尋的資料庫

→
② 被問時

檢索

找出跟問題最相關的前 K 個 chunk

→
③

增強

把找到的內容加進問題，當作上下文

→
④

生成

LLM 根據問題＋找到的內容寫出回答

chunk：長文件切成的小段，通常幾百個 token

embedding：把文字轉成一串數字（向量），意思相近的文字，數字也相近

向量資料庫：存放 embedding，能快速找出與問題「意思最接近」的內容

Part 2 · RAG

RAG 的好處與限制

好處

✓ 減少幻覺

✓ 加入新知識，不必重新訓練模型

✓ 回答可以附上來源，方便查證

限制

✗ 不能「防止」幻覺，只能減少

✗ 資訊不夠時，模型還是可能硬答

✗ 句子被斷章取義、來源互相矛盾時會答錯

✗ 每次都重新找，問過的東西不會累積

Part 2 · RAG 的盲點

切成小塊，上下文就不見了

使用者問：

「ACME 公司 2023 年第二季營收成長多少？」

資料庫裡最相關的 chunk：

「公司營收比上一季成長 3%。」

⚠️ 哪家公司？哪一季？這段文字自己看不出來 → 可能檢索不到，或被誤用

原因：RAG 把文件切成幾百個 token 的 chunk，切開時把脈絡也切掉了。

Part 2 · RAG 的改良

改良：先替每個 chunk 補上脈絡

Contextual Retrieval：讓 AI 讀整份文件，替每個 chunk 寫 50–100 個 token 的說明再建索引。
前 20 個 chunk 裡找不到相關內容的比例（越低越好）：

基本 RAG
5.7%
＋脈絡 embedding
3.7%
＋脈絡 BM25
2.9%
＋reranking
1.9%（−67%）

RAG 一路演進：Naive → Advanced → Modular RAG

知識庫小於 200,000 token（約 500 頁）時，直接整份放進 prompt 就好

Part 3 · LLM Wiki

LLM Wiki：換個思路，讓知識會累積

RAG

每次被問，都從原始文件重新找。
問過的東西不會累積。

LLM Wiki

資料進來時就讓 LLM 整理成互相連結的 wiki。
知識「編譯一次、之後持續更新」。

為什麼現在才可行？人類放棄維護 wiki，是因為整理太累；LLM 不怕做整理工作。

Karpathy 在 2026 年 4 月提出；到 2026 年 7 月，多數實作仍是原型。

Part 3 · LLM Wiki

三層架構

Schema

CLAUDE.md / AGENTS.md：寫下結構、慣例與工作流程，人和 LLM 一起修

編輯手冊
Wiki

LLM 寫的摘要頁、概念頁、比較頁，由 LLM 負責維護

百科條目
Raw

原始資料，LLM 只讀、不改

書庫裡的原書

分工：人負責挑來源、問問題；其餘的閱讀、撰寫、整理交給 LLM。

Part 3 · LLM Wiki

三個操作：Ingest · Query · Lint

Ingest 攝入

讀新來源 → 先跟人討論重點 → 寫摘要頁 → 更新相關概念頁、index、log。一個來源可能動到 10–15 頁。

Query 查詢

先讀 index，再讀相關頁，附引用回答。好的答案存回 wiki，讓探索也能累積。

Lint 健康檢查

定期找矛盾、過時說法、孤兒頁、缺少的連結。

index.md 是目錄、log.md 是只往下追加的紀錄。約 100 個來源以內，靠 index 就夠，不需要向量資料庫。

Part 4 · 比較

RAG vs LLM Wiki

面向RAG（圖書館員）LLM Wiki（百科全書）
什麼時候做事被問的時候資料進來的時候
留下什麼什麼都不留整理好的 markdown 頁面
新鮮度直接讀最新資料要重新 ingest，會落後
跨來源綜合可能漏掉跨 chunk 的關聯綜合做一次並經過審視
維護建好索引後幾乎不用需要 lint、矛盾檢查
擴展性可預期的搜尋問題變大後要靠索引或搜尋維持一致

兩者互補，不是取代：wiki 變大後，也可以對 wiki 跑 RAG。

Part 4 · LLM Wiki 的代價

LLM Wiki 的四個風險

過時

來源更新了要重新 ingest

知識漂移

每次 ingest 帶進小錯，數百次後累積

查證困難

每句話都是模型寫的

Ingestion bias

先進來的來源決定了框架

Ingestion bias 為什麼麻煩？它不是斷鏈、缺頁這種結構問題，lint 抓不到。
補救：分批、用隨機順序 lint；換順序從 raw 重建；請 AI 反駁目前的框架。

總結

三句話帶走

RAG：被問時才去找，像圖書館員。簡單、新鮮，但知識不累積，切塊會丟脈絡。

LLM Wiki：資料進來就整理好，像百科全書。會累積，但要維護、會過時、有順序偏誤。
